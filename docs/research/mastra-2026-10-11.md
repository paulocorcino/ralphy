# Research: Mastra (mastra-ai/mastra)

Date: 2026-10-11. Source: the public GitHub page, mastra.ai docs (`llms.txt`
index and the pages listed at the end), factory.mastra.ai, the Mastra blog,
and third-party articles. Nothing here was run or tested. Claims from
third-party sites are marked **(reported)**.

It is the outside input to
[agent-squads-foundations-2026-10-11.md](./agent-squads-foundations-2026-10-11.md).

## 1. What it is

- A TypeScript framework for agents, workflows, memory, RAG and evals. It runs
  inside a Node, Next.js or React app, or as its own server.
- Company: YC W25, founders from Gatsby. Funding numbers conflict between
  sources **(reported)**.
- Repo (read on 2026-10-11): 28.7k stars, 3.0k forks, ~21k commits, 269 open
  issues, 253 open PRs. Latest: `@mastra/core@1.75.0`, 2026-10-07. Several
  minor releases per week; almost every one has a breaking change.
- License: Apache-2.0 for the core. Code in `ee/` folders uses the "Mastra
  Enterprise License" (free for development, paid in production).
- Supply-chain incident, 2026-06-16/17: a contributor's npm account was taken
  over; 100+ `@mastra/*` package versions got a malicious dependency
  (`easy-day-js`) that ran in `postinstall` **(reported: Hexnode, Penligent)**.

## 2. The three layers

1. **Framework:** Agent, tools, workflows, memory, processors, evals.
2. **Harness:** what keeps an agent alive for hours or days. Durable agents,
   background tasks, goals, schedules, signals, signal providers,
   AgentController.
3. **Products on the harness:** Mastra Code (a terminal coding agent) and
   Mastra Factory (a software factory).

## 3. Orchestration

| Pattern | Primitive | Notes |
|---|---|---|
| Supervisor + subagents | `agents: {…}` on the parent; the parent picks a child by its `description` | Current way. `.network()` is deprecated (migration guide "network → supervisor"). Since `@mastra/core@1.8.0`. |
| Workflow | graph: `.then/.branch/.parallel/.foreach/.dountil/.sleep`, `.agent()` and `.tool()` as steps | Snapshots, suspend/resume, time travel (run again from a step), scheduled workflows |
| Handoff | workflow + memory; ownership moves to the next agent | No own primitive |
| Council | `.parallel()` of agents + a synthesis step | Docs say: no own primitive |

Delegation details (subagents):

- Hooks: `onDelegationStart` (rewrite the prompt, change `maxSteps`, cancel),
  `onDelegationComplete` (`bail()`, `feedback` saved to memory, rewrite the
  result), `onIterationComplete`. `hookErrorStrategy`: continue (default) or
  throw.
- Context: by default the child sees the parent's whole conversation;
  `messageFilter` narrows it. Each delegation gets a new thread. The child's
  nested tool results stay out of the parent's context unless
  `includeSubAgentToolResultsInModelContext: true`.
- `enableResultReferences`: a later delegation reuses an earlier result by id
  (`explorer-1`), only for one parent run.
- Background subagents: a child runs as a background task with `timeoutMs`;
  the parent uses `streamUntilIdle()`.
- A child's approval requests appear in the parent's stream as
  `tool-call-approval` chunks. A child cannot run client tools.
- `abortSignal` on the parent goes to the children.

## 4. Talking to a live agent

### Signals (into a thread)

| API | Thread is running | Thread is idle |
|---|---|---|
| `sendMessage()` | enters the running loop | starts a stream |
| `queueMessage()` | waits for the end of the run, then a new run | starts a run |
| `sendSignal()` (system context) | goes to the active run | wakes the thread, or is stored (`ifIdle: 'persist'`) |

- If the model has produced only reasoning, the request is cancelled and sent
  again with the new input. It does not count in `maxSteps`. After text or a
  tool call starts, input waits for the next loop boundary. Not supported on
  Inngest or across processes.
- `sendNotificationSignal()`: a durable inbox record with `source`, `kind`,
  `priority`, `summary`, `dedupeKey`. Low priority is batched into summaries.
  The agent reads the inbox with `createNotificationInboxTool()`.
- `sendStateSignal()`: a per-thread "state lane" (snapshot or delta), dedupe by
  `cacheKey`.
- Human input is wrapped as `<user name="…" sentFrom="slack">…</user>`.
  System input uses a `system-reminder` tag.
- Multi-instance: the default pub/sub is in memory; use `RedisStreamsPubSub`
  for delivery and thread leases (one owner per thread).

### Signal providers

- A class with `poll(subscriptions)` or `handleWebhook(request)`. It maps an
  outside resource (a pipeline, a repo) to subscribed threads and calls
  `notify()`. `WebhookSignalProvider` is built in.
- The subscription registry is in memory, per process.
- Notification storage: libSQL, Postgres, MongoDB.

### AgentController and Sessions (beta)

- Controller → Session → Thread. Sessions per `resourceId` and `scope` (the
  docs' example: one session per git worktree).
- Modes change instructions and tools (plan → build), with `transitionsTo`.
  The model switches apart from the mode and is stored on the thread.
- Permissions per category or per tool: `allow` / `ask` / `deny`. Event
  `tool_approval_required`; answer with `respondToToolApproval`. Grants are not
  durable.
- Interactive tools `ask_user` and `submit_plan` suspend; answer with
  `respondToToolSuspension`.
- Events: `message_start/update/end`, `display_state_changed`. The browser
  client re-syncs from `session.state()` because missed events are not sent
  again.
- Live state (grants, pending approvals, active runs) does not survive a
  restart; thread messages and settings do.

### Goals (since 1.43)

- A durable objective per thread. After each candidate answer, a judge model
  (or your scorer) returns pass or fail. Fail with budget left: the loop goes
  on with the judge's feedback. Budget `maxRuns` (default 50); at the end the
  objective is `paused`. Each evaluation emits a `goal` chunk.

### Channels

Slack, Teams, Discord, Telegram, WhatsApp, iMessage, GitHub.

## 5. Durable agents (beta, 1.45)

- The agent loop runs inside a workflow; events go through PubSub and are
  cached; `observe(runId)` replays then goes live.
- Recovery on boot (`recovery.durableAgents: 'auto'`) re-drives orphaned runs
  from the last snapshot.
- Run claim renewed every 10 s, lapses after 30 s. Fencing on Postgres,
  libSQL, Turso, in-memory.
- Backends: in-process, evented (background), Inngest.
- Warning in the docs: replay can repeat paid LLM calls and tool calls. Tools
  must be idempotent. A subagent call is one tool call, so the whole child run
  starts again.

## 6. Protocols

- **MCP** (`@mastra/mcp` v2, revision `2026-07-28`, stdio and Streamable HTTP).
  - Client: many servers, OAuth (`authenticate()`), static or per-request
    toolsets, approval per tool or by function. Security: stdio child gets a
    curated env (`inheritDefaultEnv: false`), `allowedHosts`, redirects blocked,
    server annotations treated as untrusted.
  - Server: exposes agents, tools, workflows at `/api/mcp/:id/mcp`. A tool
    `suspend()` becomes an `input_required` round. Can publish a stdio
    package. MCP Apps: a tool serves an HTML UI (`ui://`) shown in a sandboxed
    iframe.
- **ACP** (`@mastra/acp`): Mastra is the **client**. It spawns an ACP agent
  (opencode `acp`, gemini `--acp`, cline `--acp`) over stdio JSON-RPC and uses
  it as a subagent (`AcpAgent`) or a tool (`createACPTool`). Session kept alive
  by default. File reads and writes through the protocol go through the
  Workspace; the child itself is **not** sandboxed. Default permission
  answer: the first option offered.
- **A2A** (v0.3 default, v1.0 opt-in): both server and client. Agent card at
  `/.well-known/<agent>/agent-card.json`. Task states include
  `input-required`, `auth-required`, `completed`, `failed`, `canceled`,
  `rejected`. SSE streaming, `resubscribeTask()`, push notifications to a
  callback URL (best effort), optional card signing. Limit: task records and
  push configs are in memory, so resume works only on the same process.
- **SDK agents:** Claude Agent SDK, Cursor SDK, OpenAI Agents SDK wrapped as
  Mastra agents, with tracing, cost and resume by the vendor's session id.

Protocol landscape (reported, third-party):

- ACP (Zed, Aug 2025): JSON-RPC over stdio between an editor and a coding
  agent. Zed, JetBrains, an experimental Windows Terminal fork. Agents listed
  in the ACP registry: Claude Code (through an adapter), Codex, Gemini CLI,
  Copilot CLI, OpenCode.
- A2A (Linux Foundation): 150+ organizations by April 2026; version 1.x;
  the exact current version is not clear from the sources.
- Codex App Server: bidirectional JSON-RPC (stdio default), thread → turn →
  item, server-initiated approval requests, `turn/steer` and `turn/interrupt`
  (method names not checked against a schema). Schema from
  `codex app-server generate-json-schema`.

## 7. Memory

- Observational Memory: an Observer (at ~30k tokens of history) and a
  Reflector (at ~40k tokens of observations) run in the background and replace
  raw history with a dense log. History moves between ~6k and 30k tokens; the
  log stays near 40k. Compression 5–40x. A `recall` tool reads the original
  messages. Claimed 94.87% on LongMemEval with gpt-5-mini **(reported)**.
- Also: working memory, semantic recall, multi-user threads, thread clone.

## 8. Evals, processors, observability

- `runEvals` with **gates** (binary, must average 1.0) and **thresholds**
  (min, max, band). Verdict `passed` / `scored` / `failed`, for CI. Trajectory
  and tool-call-accuracy scorers, datasets, experiments, multi-turn evals.
- Processors (input/output pipeline): PromptInjectionDetector, PIIDetector,
  Moderation, TokenCostControl, ResponseCache, ToolSearch, AgentsMDInjector,
  StreamErrorRetry, CyberRefusalHandler, and more.
- Tracing: Span Query with cost per tool call, trace aggregation, exporters
  (OTel, Langfuse, Datadog, Sentry…).
- `createCodingAgent()`: workspace (local filesystem + local sandbox by
  default, on the host), task tools (`task_write/update/complete/check`),
  retry policies by error kind, optional goal.
- Workspaces and sandboxes: Docker, E2B, Daytona, Modal, Vercel, Cloudflare,
  Fly, Railway, Apple Container and more.

## 9. Mastra Factory

- Alpha July 2026, beta 2026-09-08 (docs still say alpha). Open source,
  `npm create factory@latest`, Node 22.13+.
- Sources: GitHub issues and Linear. Clients: web, mobile browser, Slack.
  Writes PRs to GitHub.
- Board: Intake → Triage → Planning → Building → Review → Done (+ Canceled).
  Each stage is a skill. Each stage is manual or auto.
- Each session clones the repo into an isolated sandbox. It never edits your
  local checkout.
- Human gates by default: accept a non-bug task before Planning; approve the
  plan (`submit_plan`) and the move to Building
  (`factory_transition_work_item`); merge is always human.
- Trust rule: an issue starts by itself only if it was created after the
  Factory and its author has write or admin access.
- Review: one card and one **separate session** per PR. Change requests go back
  to the original work session. Re-review on each push. One task can have many
  PRs; after a merge the work session **checks again if the task is complete**.
- Knowledge: a graph of cited facts kept by a curator agent ("Alexandria",
  not shipped). Plan: agents open "knowledge gap" issues for humans.
- Numbers (self-reported): 25–35% of Mastra's PRs, 50–60% of issues closed.
  The same post's charts: 17.0% of merged PRs, 28.5% of closed issues.
- Lessons they published:
  1. Full auto on an imported backlog made bursts of load and work nobody
     could review → manual/auto per stage.
  2. A wrong early assumption (triage, impact) produces PRs that get closed.
  3. A flood of low-quality PRs → a deliberately strict review.
  4. Remembering conversations is not knowing the company or the code history.
  5. The community now sends reproductions instead of PRs.
